Full-Surface Entity Editors — UI mockups

Layout proposals for docs/design/full-entity-editors.md, one per dev task. Mockups, not application code — nothing is wired to the engine and no control is functional.

Every number, label, colour and section name comes from a live browser session against the Kraktooth Goblin Camp scenario (659 nodes · 207 areas · 361 ways · 34 items · 23 characters) at 1600×1000, plus the real theme variables in static/css/style.css and the real ALL_ACTIONS / ACTION_ICONS / INVERSE_ACTIONS tables in item-view.js. Entity names are real.

What phase 1 actually delivers

  • Two mount points, one set of view modules. #entity-editor is a different element from #inspector-panel — only panel.js may write to the panel, because mixing innerHTML with lit's render() corrupts lit part tracking. No forked view modules.
  • The peek is untouched. Click still opens the panel. Additive, not a replacement — which is why the graph is dimmed rather than torn down.
  • Expand affordance in the inspector header; double-click a canvas node is the second entry point. Esc or the backdrop closes.
  • Focus discipline: focus moves to the header name on open, returns to the opening element on close.
  • No layout change yet — deliberate. Phase 1 proves the architecture and the lit constraint first.
Why not a route? /editor/character/<id> would sever canvas context, which is the whole navigation model of a canvas-based graph, and would give one entity two entry points — a second source of truth for “what am I editing”.

Item editor — actions as a 15-row enable/cost matrix

What changes, and what must not

  • A real <table> with th scope="col" / th scope="row". This is tabular data and must be navigable and announced as such — a grid of divs would fail that.
  • Colour is never the only channel. Every row keeps its text label; ACTION_COLORS becomes a row accent, not the signal.
  • INVERSE_ACTIONS becomes visible — the ⇄ marker. Today the coupling is undiscoverable until you toggle one.
  • Triggers stay a disclosure. A different task, not part of the matrix.
  • Save-on-change is unchanged — see the open question on the save model.

Design decisions worth arguing about

  • The tabs move to the header as a segmented control. That is what buys the width — the three-column body only applies to the active tab.
  • Images and Inventory stay single-column. Already narrow: Expression Pack is 7 buttons, Inventory is 20.
  • Appearance's first-impression preview must not move columns. It is a live dependent field; separating it breaks the cause-and-effect the user is there to watch.
  • Relationships gets its own row, not a column cell, so it can scroll independently.
  • The rail is generated from rendered sections, not hand-maintained — the same lesson as tools/way_property_index.py: a vocabulary declared in two places drifts.

Area editor — split properties/place with a mini-map

ui · phase 4
Measured today. The area editor has 14 sections in a 379px column with no map, and its inherently spatial sections — exits, agents present, item visibility, area event log — are stranded as text lists.
  • Environment: light 80, temp 27.6 °C, air fresh, smell "rot, straw, old food", noise quiet — plus weather, wind, humidity and a presets scope picker the docs never mention
  • Zero input[type=range] in the whole area view — the "environment sliders" the docs describe do not exist; these are text, number and select controls
  • The way view already offers VISIBLE ITEMS IN <AREA> with 207 options per side — strong evidence that visibility is spatial and is currently edited as a dropdown

The payoff, and the open dependency

  • Spatial sections stop being text. Exits, agents and item visibility gain a map beside them. The VISIBLE ITEMS IN <AREA> selector is the tell — 207 options for a spatial relation.
  • All nine environment controls in one block, because they are read together, and labelled by their real control types rather than as "sliders".
  • The event log is read-only and scroll-locked — context, not a field.
  • Open dependency: whether below 900px is a real target is undecided, so the stacked variant is deliberately not drawn. Confirm the responsive story before building one.

What these mockups are not

Boundaries

  • Not application code. No engine calls, no lit-html, nothing wired. These are layout proposals.
  • Not a pixel spec. Proportions are indicative. The measured numbers (380px, 3346px, 15 actions, 14 sections, 207 areas) are real; the drawn sizes are not contractual.
  • Not everything is designed. The save model, deep links, multi-entity 2-up compare, the mobile story, and whether the way editor earns a fifth layout are all still open in docs/design/full-entity-editors.md.
  • Not verified behaviour. These are proposals. Per the repo's own rule, none of this may be called shipped until it has been watched working in a live browser.
